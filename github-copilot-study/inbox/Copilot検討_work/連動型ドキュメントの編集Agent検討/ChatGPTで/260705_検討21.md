# 私の一番のおすすめ構成

例えば、今回のソフトウェア開発プロジェクト用に、

```text
Project
└─ ソフトウェア開発ドキュメント管理
```

を作ります。

その中を概念的に次のように使います。

```text
Project: ソフトウェア開発ドキュメント管理

├─ Project instructions
│   └─ 共通方針
│
├─ Project files
│   ├─ 調査報告書
│   ├─ 見積書
│   ├─ 要件定義書
│   ├─ 基本設計書
│   ├─ 機能仕様書
│   ├─ 詳細設計書
│   ├─ テスト設計書

│
├─ Chat: 整合性レビュー
│

```

Project内のチャットは、プロジェクトに追加したファイルとプロジェクト指示を共有コンテキストとして利用できます。([OpenAI Help Center][1])

# 1. Project instructionsには「共通ルール」だけを書く

GitHub Copilotで作った `doc-sync.agent.md` 全文を、そのままProject instructionsに入れることは、私はあまりおすすめしません。

理由は、Project instructionsはそのProject内のすべてのチャットに影響するためです。ChatGPTではProjectに独自の指示を設定でき、Project内の作業にその指示が使われます。([OpenAI Help Center][1])

例えばProject instructionsには、次くらいを書きます。

# プロジェクトの目的

本プロジェクトでは、ソフトウェア開発に関するドキュメントの作成、レビュー、変更反映、整合性確認を行う。

# 基本方針

* 要件、設計、仕様、テスト、運用の整合性を重視する。
* 変更内容を単純な文字列置換として扱わず、各記述の文脈を確認する。
* 変更履歴、調査経緯、不採用理由として残すべき情報を誤って削除しない。
* ユーザーが指定していない仕様を推測で追加しない。
* 不明点があっても、確定している範囲の分析や作業は進める。
* 既存ドキュメントの文体、章構成、用語、項番体系を尊重する。
* 修正後は、変更前情報の残存、項番、ID、参照関係、ドキュメント間の整合性を確認する。

ここでは、**すべてのチャットで共通して守ってほしい内容だけ**を置きます。

Copilotでいうと、

```text
copilot-instructions.md
```

に近い役割として考えると分かりやすいです。

# 2. `doc-sync` は専用チャットにする

Project内に、

```text
ドキュメント同期・修正
```

というチャットを1つ作ります。

最初のメッセージに、先ほど作った `doc-sync.agent.md` 相当の指示を与えます。

ただし、完全なAgent.mdを毎回貼る必要はありません。

例えばProject filesに、

```text
doc-sync-instructions.md
```

として保存しておいて、

```text
doc-sync-instructions.md の方針に従って、
今回の変更を関連ドキュメントへ反映してください。

変更内容:
ファイル出力形式をJSONからXMLへ変更します。

理由:
顧客環境では外部ライブラリを利用できないためです。
```

のように使う方法が考えられます。

Projectには参考ファイルをアップロードしてチャットから利用できるため、この方式と相性がよいです。([OpenAI Help Center][1])

---

# 3. 影響調査と修正は「まずチャットを分ける」で十分だと思います

GitHub Copilotのときに、

* 影響調査Agent
* 修正Agent
* 大規模変更Agent
* 小規模変更Agent

を分けるか検討しました。

ChatGPTでは、現時点ではもっと単純に、

```text
Chat A: 変更影響調査
Chat B: ドキュメント修正
```

と分けるだけでも十分だと思います。

例えば。

## 変更影響調査チャット

```text
今回の変更について影響調査をしてください。

まだドキュメントは修正しないでください。

以下を整理してください。
・影響するドキュメント
・影響する章、項目
・想定される修正内容
・修正不要と考えられるドキュメント
・要確認事項
```

## 修正チャット

```text
先に整理した変更影響をもとに、
必要なドキュメントの修正案を作成してください。

修正後は、
・変更前仕様の残存
・項番
・参照関係
・テストとの整合性
・運用との整合性
を確認してください。
```

これなら、**Agentを量産する必要がありません**。

# 4. `copilot-config-reviewer` に相当するものも別チャットでよいです

先ほどの

```text
copilot-config-reviewer.agent.md
```

に相当するものは、ChatGPT Projectでは、

```text
Chat: ChatGPT運用構成レビュー
```

を作るだけでも十分です。

ただし今回レビュー対象は、Copilot構成ではなくChatGPTの使い方になるので、役割を少し変えます。

例えば、

```text
このProjectの現在の運用方法をレビューしてください。

確認対象:
・Project instructions
・アップロードファイルの構成
・用途別チャットの分け方
・定型プロンプト
・Custom GPT化の必要性

以下の観点で改善案を検討してください。
・不要なコンテキストの削減
・役割分担
・再利用性
・保守性
・作業効率

改善効果が明確でない場合は、現状維持を推奨してください。
```

とします。

私は、このReviewerも**毎回実行する必要はない**と思います。

例えば、

```text
Project作成
↓
5～10回程度使用
↓
構成レビュー
↓
必要なら改善
```

くらいがよいです。

# Custom GPTは使わなくてよいのか

ここが重要ですが、私の結論は、

> **最初はProjectだけでよい**
>
> ただし、複数Projectで再利用したくなったらCustom GPTを検討する

です。

Custom GPTは、特定用途向けにInstructions、Knowledgeファイル、Capabilitiesなどを設定できる仕組みです。([OpenAI Help Center][2])

したがって例えば、

```text
Project A
顧客管理システム

Project B
DB構築学習

Project C
SkillBase

Project D
社内ツール開発
```

があり、全部で

```text
ドキュメント変更影響調査
```

を行いたいなら、

```text
Custom GPT
└─ Software Document Sync Reviewer
```

を作る価値があります。

概念的には、

```text
Custom GPT
    汎用的な作業方法

Project
    プロジェクト固有資料

Chat
    今回の変更依頼
```

という三層にできます。

# ProjectとCustom GPTは併用できます

現在の公式ヘルプでは、既存のProjectチャット内でCustom GPTを利用できます。ただし、最初のメッセージからCustom GPTを使うとProject外のGPTチャットとして開始されるため、利用方法には注意が必要です。([OpenAI Help Center][1])

そのため、将来的には、

```text
Project
└─ 開発案件A
    ├─ 要件定義書
    ├─ 基本設計書
    ├─ テスト仕様書
    │
    └─ Chat
         ↓
      Doc Sync GPTを利用
```

という運用も可能です。

ただし、私は最初からここまで作り込まない方がよいと思います。

# 私がToshiさんにおすすめする具体的な構成

Toshiさんの場合は、Copilotでも「最初からAgentやSkillを細かく分けすぎず、使いながら整理する」方針を取っています。

ChatGPTでも同じ考え方でよいと思います。

## STEP 1：Projectを1つ作る

例えば、

```text
Software Development Documents
```

あるいは日本語で、

```text
ソフトウェア開発ドキュメント
```

です。

---

## STEP 2：Project instructionsを設定

内容は、

```text
・推測で仕様追加しない
・文脈を見て変更する
・履歴を誤削除しない
・関連ドキュメント間の整合性を見る
・既存形式を尊重する
```

程度の共通原則です。

---

## STEP 3：ファイルを置く

例えば、

```text
01_research.md
02_estimate.md
03_requirements.md
04_basic_design.md
05_function_spec.md
06_detail_design.md
07_test_design.md
08_test_spec.md
09_operation_design.md
10_operation_manual.md
```

です。

Projectでは参考ファイルをアップロードしてチャットから利用できます。([OpenAI Help Center][3])

---

## STEP 4：チャットを用途別に作る

最初は3つでよいと思います。

```text
① 変更影響調査

② ドキュメント同期・修正

③ 構成改善レビュー
```

私は最初から、

```text
小規模変更
大規模変更
JSON変更用
機能追加用
削除用
```

などには分けません。

---

## STEP 5：定型プロンプトをMarkdownで管理

例えばProject filesとして、

```text
prompts/
├─ impact-analysis.md
├─ doc-sync.md
└─ project-review.md
```

相当のファイルを持つ方法もあります。

ただし、ChatGPTのProject内でフォルダそのものとして管理できるという意味ではなく、**ファイル名で役割を整理するイメージ**です。

例えば、

```text
prompt_impact-analysis.md
prompt_doc-sync.md
prompt_project-review.md
```

として置く方が管理しやすいと思います。

# Project-only memoryについて

ソフトウェア開発案件ごとに情報を明確に分離したいなら、新しいProject作成時に利用可能な **project-only memory** は相性がよいと思います。

この設定では、そのProject内の他の会話を参照できますが、Project外の保存メモリや会話を参照せず、Projectの内容も外部チャットに持ち出さない形になります。([OpenAI Help Center][4])

例えば、

```text
顧客A Project
顧客B Project
個人学習 Project
```

の情報を混ぜたくない場合に向いています。

これは業務案件のようにプロジェクト境界を重視する用途では、かなり有効だと思います。
