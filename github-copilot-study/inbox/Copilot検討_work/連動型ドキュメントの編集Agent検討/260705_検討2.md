# なぜ最初からAgent + Skillにしなくてよいか

今回の場合、まだ実際に使っていないので、

> どの処理が毎回共通になるのか

がまだ分からないからです。

例えば、現在考えている

```text
ドキュメント別確認観点
```

はSkill化できそうに見えます。

しかし、実際に使ってみると、

```text
調査報告書はほとんど修正しない

見積書も変更後はあまり触らない

基本設計～テスト仕様の確認が圧倒的に多い
```

となるかもしれません。

逆に、

```text
項番調整
参照関係確認
変更前用語の再検索
```

の方が、独立Skillとして重要になる可能性もあります。

まだ使っていない段階で分割すると、**実際の作業単位ではなく、想像上の分類でSkillを作ることになる**のが少し気になります。

Skillは、専門的な手順、スクリプト、例、リソースなどを再利用可能な能力として持たせ、関連時に必要な内容だけ読み込む仕組みです。そのため、繰り返し使う手順が見えてから切り出す方が自然です。([Visual Studio Code][2])

# 私なら3段階で育てます

## 第1段階：Agent 1個

今はここでよいと思います。

```text
doc-sync.agent.md
```

内部に、

```text
1. 変更内容整理
2. 影響調査
3. 修正方針決定
4. ドキュメント修正
5. 項番調整
6. 再検索
7. 整合性確認
8. 結果報告
```

を全部書きます。

そして依頼時のプロンプトで動作範囲を変えます。

### 影響調査だけ

```text
この変更について、関連ドキュメントへの影響調査のみ行ってください。
まだファイルは修正しないでください。
```

### 調査＋修正

```text
この変更について影響範囲を調査し、
必要なドキュメントを修正してください。
```

### 小規模変更

```text
小規模な変更として扱ってください。
変更内容に直接関係する箇所を中心に確認・修正してください。
過剰な全体調査は不要です。
```

### 大規模変更

```text
大規模な仕様変更として扱ってください。
要件、設計、仕様、テスト、運用まで横断的に確認してください。
```

まずはこれで十分だと思います。

## 第2段階：Promptを追加する

使ってみて毎回同じ指示を書くようになったら、Agentを増やす前にPrompt fileを検討するとよいです。

例えば、

```text
.github/
├── agents/
│   └── doc-sync.agent.md
│
└── prompts/
    ├── doc-impact-check.prompt.md
    ├── doc-small-change.prompt.md
    └── doc-full-update.prompt.md
```

という形です。

VS CodeのPrompt fileは、よく使うタスクを独立したMarkdownとして定義し、チャットから手動で呼び出せます。また公式ドキュメントでも、Custom Agentの既定動作を特定用途向けに上書きする例として、最小限の計画作成などが挙げられています。([Visual Studio Code][3])

今回に当てはめると、

```text
Doc Sync Agent
    │
    ├─ /doc-impact-check
    │      影響調査のみ
    │
    ├─ /doc-small-change
    │      小規模変更
    │
    └─ /doc-full-update
           全体横断修正
```

という構成がかなり自然です。

私は、**「大規模用Agent」「小規模用Agent」に分ける前に、このPrompt方式を試すことを強くおすすめします。**

# 「影響調査Agent」と「修正Agent」は分けるべきか

現時点では、**分けなくてよい**と思います。

理由は、影響調査と修正はかなり密接だからです。

```text
影響調査
↓
この記述は修正対象
この記述は過去経緯なので維持
このファイルは修正不要
↓
修正
```

という判断は連続しています。

Agentを分けると、

```text
Impact Analyzer
        ↓
     結果出力
        ↓
Doc Updaterが再度理解
        ↓
     修正
```

となります。

これは将来的には意味がありますが、最初からやると、

* Agent間で判断基準がズレる
* 調査結果の受け渡し形式を設計する必要がある
* 同じファイルを再調査する可能性がある
* 問題発生時にどちらを直すべきか分かりにくい

という管理コストが増えます。

したがって、今は

```text
Doc Sync Agent

[フェーズ1]
影響調査

[フェーズ2]
修正

[フェーズ3]
検証
```

という**1 Agent内のフェーズ分離**で十分です。

# 「大規模用」と「小規模用」も今は分けなくてよいです

これも同様です。

実際には、変更は綺麗に2種類には分かれないと思います。

例えば、

```text
小規模
中規模
大規模
緊急修正
設計変更
実装制約対応
機能追加
機能削除
不具合修正
```

など、徐々にパターンが増えていく可能性があります。

そこでAgentを作るたびに、

```text
doc-small-change
doc-large-change
doc-bugfix
doc-feature-add
doc-feature-remove
doc-design-change
```

と増やすと、使い分けが難しくなります。

最初はAgent側に、

```md
# 作業範囲の調整

ユーザーの指示内容と変更規模に応じて、確認範囲を調整する。

ユーザーから「影響調査のみ」と指示された場合は、ファイルを変更しない。

ユーザーから確認範囲が指定された場合は、その範囲を優先する。

変更規模が小さい場合でも、直接関連する後続工程のドキュメントについては修正漏れがないか確認する。

大規模な変更、機能追加、機能削除の場合は、要件・設計・テスト・運用まで横断的に確認する。
```

程度でよいと思います。

# Skill化するタイミング

私なら、次のような兆候が出たらSkill化します。

### ① Agentが長くなりすぎた

例えば、

```text
doc-sync.agent.md
500行
```

のようになった場合です。

そのとき、

```text
Agent
├─ 役割
├─ 判断ルール
└─ 全体フロー

Skill
├─ ドキュメント別確認観点
├─ 項番整合性チェック
└─ トレーサビリティ確認
```

と切り出します。

### ② 同じ手順を別Agentでも使いたくなった

例えば将来、

```text
Doc Sync Agent
Test Review Agent
Requirements Review Agent
Operation Doc Agent
```

を作り、

どれも

```text
項番・参照番号整合性チェック
```

を使いたくなった場合です。

この段階なら、

```text
doc-reference-integrity
```

のようなSkillを作る意味があります。

### ③ Agent内の一部分を単独で実行したくなった

例えば、

```text
修正は不要。
ドキュメント間のトレーサビリティだけ確認したい。
```

という用途が頻繁に出てきた場合、

```text
traceability-check
```

をSkill化するのは有効です。

## 結論

**現時点では、複数Agent・複数Skillを作る必要はないと思います。**

私の第一案は、

```text
.github/
└── agents/
    └── doc-sync.agent.md
```

だけで開始です。

そして、まずプロンプトで、

```text
影響調査のみ
調査＋修正
小規模変更
大規模変更
```

を切り替えます。

その後、使っていて定型化した呼び出し方は **Prompt file** にし、繰り返し使う専門的な手順は **Skill** にし、役割そのものが独立してきた場合だけ **別Agent** にする、という順番が一番きれいだと思います。

特に今回の場合、**「影響調査」「修正」「小規模」「大規模」は、現時点ではAgentの違いというより実行モードの違い**と考えるのが自然です。Prompt fileは同じCustom Agentに対してタスク固有の指示を与えられるので、この使い分けと相性がよいです。([Visual Studio Code][3])

次に作るなら、まずSkillなしの前提で、**実運用を意識した `doc-sync.agent.md` の全文**を作成するのがよいと思います。
