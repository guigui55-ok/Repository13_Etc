Question:
今仕事でGithubCopilotを使用しています。（プレミア枠あり） 私は、Copilotには主に以下の機能があると思っています。 * copilot-instructions.md（このプロジェクトではどう振る舞うべきか） * *.instructions.md（特定ファイル群にだけ適用。） * AGENTS.md * Custom Agents（*.agent.md）（特定専門AIを作る） * SKILL.md（Agent Skills）（特定タスク知識をモジュール化」） * Prompt Files（*.prompt.md）（再利用可能プロンプト」） * MCP（AIへ外部ツールを接続） * Hooks（AI処理前後にスクリプト実行） * Copilot Workspace * GithubCLI 仕事では既存アプリ（大規模）があり、機能追加時の仕様の調査や設計検討、実装に使用しています。 機能追加時の仕様の調査と機能追加の設計をするときに、上記の機能をいくつか使えばかなり効率的に作業できると思っています。 どのようにしたらよいか、提案していただけますか？


Answer:
はい。大規模な既存アプリなら、**「調査用」「設計用」「実装用」でCopilotの役割を分ける**のが一番効果的です。

## おすすめ構成

| 用途        | 使う機能                                     | 役割                                |
| --------- | ---------------------------------------- | --------------------------------- |
| 全体ルール     | `.github/copilot-instructions.md`        | プロジェクト共通ルール、ビルド方法、禁止事項            |
| 領域別ルール    | `.github/instructions/*.instructions.md` | C#、DB、画面、通信、テストなど領域別の注意点          |
| Agent向け手順 | `AGENTS.md`                              | 大規模調査時の進め方、確認観点、成果物形式             |
| 専門AI      | `*.agent.md`                             | 仕様調査Agent、設計レビューAgent、実装Agentを分ける |
| 再利用作業     | `*.prompt.md`                            | 「影響調査して」「設計案を出して」など定型プロンプト化       |
| 外部連携      | MCP                                      | GitHub Issue、設計書、DB定義、チケット等を読ませる  |
| 自動確認      | Hooks                                    | ビルド、テスト、静的解析、フォーマット確認             |
| 実作業       | Copilot CLI / Agent                      | 調査・修正・テストを小単位で依頼                  |

GitHub公式でも、リポジトリ全体の指示は `.github/copilot-instructions.md`、パス別指示は `.github/instructions/**/*.instructions.md`、Agent向け指示は `AGENTS.md` などで分けられる形になっています。([GitHub Docs][1]) また、Custom Agents は用途別に振る舞い・利用ツール・MCP設定を持たせられる仕組みです。([GitHub Docs][2])

## 実務での使い方

機能追加時は、いきなり実装させず、以下の流れにすると安全です。

### 1. 仕様調査Agentに調査だけさせる

役割は「コードを変更しない調査専用」にします。

依頼例：

```text
この機能追加に関係しそうな画面、クラス、DB、設定ファイル、既存処理フローを調査してください。
コード変更はしないでください。
結果は以下で出してください。

- 関係ファイル一覧
- 処理フロー
- 変更候補
- 影響範囲
- 不明点
- 確認すべき仕様
```

ここで使うのは、**Custom Agent + AGENTS.md + Prompt Files** が向いています。

### 2. 設計検討Agentに設計案を出させる

調査結果をもとに、複数案を出させます。

```text
上記の調査結果をもとに、機能追加の設計案を出してください。
既存コードへの影響が小さい案を優先してください。

出力：
- 推奨案
- 代替案
- 変更対象クラス
- 追加クラス
- 既存処理への影響
- テスト観点
- リスク
```

ここでは **Prompt Files** にしておくと、毎回同じ品質で設計レビューできます。

### 3. 実装Agentに小さく実装させる

実装は一括ではなく、

```text
まずは設計案のうち、○○クラスだけ修正してください。
他のファイルは変更しないでください。
変更後、ビルドエラーになりそうな点を説明してください。
```

のように小分けがよいです。

## 特におすすめの運用

大規模既存アプリでは、`copilot-instructions.md` に以下を必ず書くのがよいです。

```md
# Project Rules

- 既存仕様を壊さないことを最優先する。
- 大きな変更を一度に行わない。
- 変更前に、関連ファイル・処理フロー・影響範囲を調査する。
- 推測で実装しない。不明点は「不明点」として列挙する。
- 既存の命名規則、例外処理、ログ出力、DBアクセス方式に合わせる。
- 変更後は、ビルド方法・確認方法・テスト観点を提示する。
- C#は既存プロジェクトのバージョンに合わせ、不要に新しい構文を使わない。
```

これは、ユーザーさんのように **C# / VB.NET / 既存大規模業務アプリ / 機能追加中心** の作業にはかなり相性が良いです。

## 結論

まずは全部を一気に使うより、次の4つから始めるのがおすすめです。

1. `.github/copilot-instructions.md`
2. `.github/instructions/*.instructions.md`
3. `investigate-feature.prompt.md`
4. `design-feature-change.prompt.md`

その後、調査・設計が安定してきたら、`*.agent.md`、MCP、Hooks を追加するとよいです。
