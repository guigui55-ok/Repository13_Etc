# Copilotの“デフォルト”はどうなっているか

おおよそですが、現在のCopilot系LLMは内部的に、

* 一般的なクリーンコード
* 可読性重視
* コメント推奨
* テスト推奨
* 例外処理推奨
* モダン構文推奨
* リファクタ推奨
* DRY原則
* SOLID原則

みたいな「一般Web開発寄り」の思想をかなり持っています。

つまり、放置するとかなり高確率で：

```csharp
var result = items
    .Where(x => ...)
    .Select(x => ...)
    .ToList();
```

とか、

```csharp
async Task<Result>
```

とか、

```text
責務分離のため新規クラス作成
```

とか、

```text
既存コード整理しましょう
```

方向へ寄ります。

# 業務システムで問題になるところ

ユーザーさんのような、

* WinForms
* .NET Framework 4.7
* レガシー
* 長寿命業務システム
* 保守重視
* 既存互換性重視

では、AIの“善意”が逆に危険です。

例えばAIは普通に：

* async化
* LINQ化
* DI導入
* MVVM化
* 共通化
* リファクタ
* 命名変更
* ファイル分割

をやりたがります。

でも実務では：

```text
「既存に合わせろ」
```

が最優先ですよね。

だから、

```md
既存実装優先
大規模変更禁止
async禁止
```

みたいな指示は、かなり価値があります。

---

# 逆に「不要な指示」

これは結構あります。

例えば：

```md
可読性を重視する
```

```md
例外処理を行う
```

```md
テストを考慮する
```

これは元々かなりデフォルトで入っています。

なので省略可能です。

---

# 一番価値がある指示

実務では、以下が非常に効きます。

## ① 禁止事項

これは超重要です。

```md
不要なリファクタ禁止
既存命名変更禁止
async化禁止
```

AIは放置するとかなり変更したがるため。

---

## ② 業務固有ルール

これはAIは知らないので必須です。

```md
Shift-JIS維持
BOM維持
AppLogger使用
```

こういうの。

---

## ③ 調査優先

これも重要。

```md
実装前に影響範囲調査
```

を入れないと、
いきなりコード書き始めます。

---

# 実務でおすすめの「薄い版」

実際は、かなり短くしても効きます。

例えば：

```md
# Copilot Instructions

- 既存仕様維持を最優先
- 不要なリファクタ禁止
- 既存コードスタイルを優先
- async/await は原則禁止
- AppLogger を使用
- Shift-JIS/BOM に注意
- 実装前に影響範囲を調査
- 不明点は推測せず列挙
```

これだけでもかなり変わります。

# コンテキスト節約について

これは正しい考えです。

特に大規模Workspaceだと、

```text

↓
毎回大量投入
↓
本来のコード理解に使うトークン減少
```

が起きます。

なのでおすすめは：

# ベースは薄く

```text

```

は短め。

# 実は一番重要なのは「Prompt」

かなり重要なのですが、

```text
instructions
```

より、

```text
今回何をしてほしいか
```

のほうが影響が大きいです。

つまり：

```text
「コード変更せず調査だけ」
```

これが最重要です。

逆にこれを書かないと、
instructionsが良くても普通に実装始めます。
