はい、かなりよい流れです。
ただ、今回のケース（既存変更不可・別Editionのみ変更・DB変更あり）だと、少し順番を変えると事故が減ります。

おすすめはこうです。

```text
① 現状調査
↓
② ストアド変更設計
↓
③ DB（別Edition）へ手動反映
↓
④ SSMSでストアド単体確認
↓
⑤ クライアント実装変更
↓
⑥ クライアント疎通確認
↓
⑦ 実装Fix
↓
⑧ テスト
↓
⑨ リリース手順整理
```

もう少し具体化します。

---

## ① 現状調査（先にここを厚めに）

確認対象：

### サーバー側

* ログインストアド名
* 引数一覧
* 戻り値形式（SELECT / OUTPUT / RETURN）
* ユーザー認証フロー
* テーブル一覧取得処理の位置
* 他ストアド呼び出し有無

### クライアント側

* ストアド呼び出し箇所
* SqlCommand生成箇所
* DataReader / DataSet受け取り方
* エラー処理

ここで特に確認したいのは、

```text
ストアド結果の列数増加が既存受け取りに影響するか
```

です。

---

## ② ストアド変更設計

ここで決める。

例：

```text
追加引数
@ClientEditionId

追加戻り値
ServerEditionId

エラーコード
EDITION_MISMATCH
```

ここは設計書レベルで軽くまとめる。

---

## ③ DB（別Edition）へ手動反映

SSMSで。

実行前：

```sql
EXEC sp_helptext 'dbo.LoginUser'
```

退避：

```sql
EXEC sp_helptext 'dbo.LoginUser'
```

→ ファイル保存

反映：

```sql
ALTER PROCEDURE
```

---

## ④ SSMSでストアド単体確認 ←重要

ここはクライアント触る前にやった方がよいです。

確認ケース：

### 正常

```sql
EXEC LoginUser
 @User='aaa',
 @Pass='bbb',
 @ClientEditionId='EDITION_B'
```

期待：

```text
LoginResult=1
```

---

### 既存クライアント想定

```sql
EXEC LoginUser
 @User='aaa',
 @Pass='bbb'
```

期待：

```text
LoginResult=0
ErrorCode=EDITION_MISMATCH
```

---

### 不正値

```sql
EXEC LoginUser
 @User='aaa',
 @Pass='bbb',
 @ClientEditionId='XXX'
```

期待：

```text
LoginResult=0
```

---

## ⑤ クライアント変更

変更箇所：

```csharp
cmd.Parameters.AddWithValue(
    "@ClientEditionId",
    "EDITION_B");
```

戻り取得：

```csharp
serverEditionId
```

比較：

```csharp
if(serverEditionId!="EDITION_B")
{
    throw;
}
```

## ⑨ リリース手順整理（意外と重要）

今回DB変更があるので、

```text
① DB更新
② サーバー配置
③ クライアント配布
```

順序を決める。

特に、

```text
クライアント先行配布
```

すると一時的に全ログイン失敗になる可能性があります。

---

一つだけ追加すると、今回なら**「実装Fix」より前にSSMS単体試験を入れる**のがかなりおすすめです。クライアントデバッグ時間が減ります。
