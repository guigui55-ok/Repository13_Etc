# 2. CopilotとChatGPTに「同じ作業」をさせる場合

はい、**この場合は手順を変えた方がよいです**。

前回の案では、

```text
Copilot
→ 実ファイル検索・編集

ChatGPT
→ 方針検討・レビュー
```

としていました。

しかし今回の目的なら、

```text
同じ変更要求
       │
       ├─ Copilotで処理
       │
       └─ ChatGPTで処理
```

という**並列構成**にした方がよいです。

私はこの考え方をかなりおすすめします。

## 目指す形

例えば同じ変更要求に対して、

```text
CR-0001
JSON出力 → XML出力
```

があった場合、

### 職場

```text
VS Code
↓
GitHub Copilot
↓
影響調査
↓
ドキュメント修正
↓
整合性レビュー
```

### 自宅

```text
ChatGPT Project
↓
影響調査
↓
ドキュメント修正案
↓
整合性レビュー
```

### 自宅・比較用

```text
VS Code
↓
Copilot Free
↓
同じ指示を実行
```

とします。

これなら、

* 影響調査の深さ
* 修正漏れ
* コンテキスト維持能力
* 指示追従性
* 長い処理への耐性
* 説明の分かりやすさ
* 不要変更の多さ

などを実体験として比較できます。

Toshiさんが言われている、

> それぞれのAIの違いや理解も深まる

という目的には、この方法がかなり向いています。

前回は、

```text

chatgpt/
```

をかなり明確に分けました。

今回も分けること自体はよいですが、**共通ワークフローを中心に置いた方がよい**と思います。

例えば、

```text
software-project/

│   ├── agents/
│   │   ├── doc-sync.agent.md
│   │   └── copilot-config-reviewer.agent.md

│
├── ai/
│   ├── workflows/
│   │   ├── impact-analysis.md
│   │   ├── doc-sync.md
│   │   └── consistency-review.md
│   │
│   ├── chatgpt/
│   │   └── project-instructions.md
│   │
│   └── logs/
│       ├── decisions.md
│       └── ai-comparison.md
│
├── docs/
│   ├── 00_change_requests/
│   ├── 01_research/
│   ├── estimate.md
│   ├── requirements.md
│   ├── basic_design.md
│   ├── function_spec.md
│   ├── detail_design.md
│   ├── test_design.md
│   ├── test_spec.md
│   ├── operation_design.md
│   └── operation_manual.md
│
├── src/
├── tests/

```

私は今回、前回の

```text
chatgpt/
```

より、

```text
ai/
```

の方が合っていると思います。

理由は、ChatGPT専用プロジェクトではなく、

```text
Copilot
ChatGPT
将来の別AI
```

で同じワークフローを比較・検証できるからです。

---

## 重要なのは「共通指示」と「製品固有指示」を分けることです

例えば、

```text
ai/workflows/impact-analysis.md
```

は、CopilotでもChatGPTでも使える内容にします。

例えば、

```text
変更内容について関連ドキュメントへの影響を調査する。

確認項目:
1. 変更内容
2. 影響するドキュメント
3. 影響する章・項目
4. 想定される修正
5. 修正不要と判断した項目
6. 上流工程への影響
7. 下流工程への影響
8. 要確認事項
9. 残存リスク

変更前の用語が存在するだけで修正対象としない。
変更履歴、調査経緯、不採用理由、比較説明として
残す必要がないか確認する。
```

これはAI共通です。

一方、

```text
.github/agents/doc-sync.agent.md
```

では、

```text
リポジトリ内を検索する
対象ファイルを読み込む
編集する
差分を確認する
```

というCopilot固有の実行手順を追加します。

ChatGPT側では、

```text
ai/chatgpt/project-instructions.md
```

にChatGPT Project向けの前提を置きます。

この構成なら、

> **思考手順は共通、実行方法だけAIごとに違う**

という比較ができます。

私はこれが今回の目的には最も合っていると思います。

# 5. 同じ作業をさせるためのおすすめ運用

例えば変更要求 `CR-0001` を実施するとします。

## Step 1：変更要求をローカルで共通管理

```text
docs/00_change_requests/
└── CR-0001_json-to-xml.md
```

これを比較の入力条件にします。

---

## Step 2：Copilotで実施

例えば、

```text
CR-0001を対象として影響調査を行ってください。
ai/workflows/impact-analysis.md の観点に従ってください。
```

---

## Step 3：ChatGPTで同じ変更を実施

ChatGPT Projectで、

```text
CR-0001の変更内容は以下です。

（変更要求を貼る）

Project Sourcesを対象として、
影響調査を行ってください。

ai/workflows/impact-analysis.md と同じ観点で、
以下を確認してください。
...
```

とします。

完全に同じプロンプトにしなくても構いません。

重要なのは、

> 入力条件と評価観点を同じにする

ことです。

CopilotとChatGPTでは利用可能なコンテキストやファイル操作の方法が異なるため、「文字列として100%同じプロンプト」を目指すより、同じ目的・同じ確認項目・同じ成果物形式にする方が公平です。

---

## Step 4：必要なら結果を比較する

例えば、

```text
ai/logs/ai-comparison.md
```

に、

```text
# CR-0001 AI比較

## Copilot

### 良かった点
- 詳細設計の該当箇所を正確に特定
- 実ファイル修正が速い

### 気になった点
- 運用手順書への波及を見落とした


## ChatGPT

### 良かった点
- 上流・下流の関係整理が分かりやすい
- 運用影響まで発見

### 気になった点
- 実ファイルとの差異確認に手作業が必要
```

程度に残すと面白いと思います。

ただし、毎回これをする必要はありません。

AI比較そのものが主目的になって、本来の開発学習が進まなくなる可能性があるからです。

私なら、最初の数ケースだけ比較します。

# 6. 自宅のCopilot Freeはどう位置づけるか

私は次の位置づけをおすすめします。

```text
職場Copilot有料版
    → 本格的なCopilot Agent運用

自宅ChatGPT有料版
    → 同じ開発フローの主力環境

自宅Copilot Free
    → 小規模ケースで比較・動作確認
```

つまり、自宅では、

> **ChatGPTを主、Copilot Freeを比較対象**

くらいでよいと思います。

長いドキュメント群を使った影響調査や同期処理では、利用可能なコンテキスト量や製品側の制限によって実行感が変わるため、Copilot Freeに完全再現を求めるより、「どの規模まで実用的に動くか」を見る方が有益です。

# 7. Project名は `Software Development Documents` でよいか

今回の追加説明を踏まえると、私は**変更をおすすめします**。

`Software Development Documents` は、

> ソフトウェア開発ドキュメントを作成・管理する場所

という印象が強いです。

ですがToshiさんの用途は、

* 開発ドキュメント作成
* 要件や設計の相談
* 小～中規模ツール開発
* コード相談
* 実装方針検討
* テスト設計
* AIワークフロー検証

まで含みそうです。

そのため、少し広い名前の方がよいです。

## 私の第一候補

```text
Software Development Workspace
```

です。

日本語なら、

```text
ソフトウェア開発ワークスペース
```

です。

これが一番合っていると思います。

### 理由

`Documents` だと、

```text
要件定義
設計書
テスト仕様書
運用設計書
```

中心に見えます。

一方、`Workspace` なら、

```text
調査
相談
設計
実装
レビュー
ドキュメント
小規模ツール開発
AI活用実験
```

をすべて自然に含められます。

公式にもChatGPT Projectsは、単なる文書保管ではなく、チャット・参考ファイル・指示を集約して継続的な作業を進めるワークスペースとして説明されています。([OpenAI Help Center][1])

---

## 他の候補との比較

| Project名                       | 印象        | 私の評価 |
| ------------------------------ | --------- | ---- |
| Software Development Documents | 文書作成中心    | △    |
| Software Development           | 少し広すぎる    | ○    |
| Software Development Workspace | 開発作業全般    | ◎    |
| Software Engineering Workspace | より技術・設計寄り | ○    |
| Development Lab                | 実験・学習寄り   | ○    |
| Software Engineering Lab       | 学習＋検証向け   | ○    |

Toshiさんの場合、

**実務的なドキュメント作成と、個人ツール開発・AI活用学習の両方**

なので、

> **Software Development Workspace**

を第一候補にします。
