# 修正した方がよい点

## 1. Agentのfrontmatterの `skills:` は外した方がよいです

添付案には次の記述があります。

```yaml
skills: [doc-change-propagation]
```

現在のVS Code公式ドキュメントで、`.agent.md` のfrontmatterとして説明されている主な項目は `name`、`description`、`argument-hint`、`tools`、`agents`、`model`、`user-invocable`、`handoffs` などで、`skills` は掲載されていません。 ([Visual Studio Code][1])

したがって、私は次のようにする方を勧めます。

```md
---
name: Doc Sync
description: 開発中の変更内容を関連ドキュメントへ横断的に反映します。
tools: ['search', 'edit']
---

# 役割

変更内容を分析し、関連する開発ドキュメントへの影響を調査して、
必要な変更を横断的に反映する。

この作業では、利用可能な場合は
doc-change-propagation Skill の手順を使用する。
```

Skillは関連性に応じてCopilotが読み込む仕組みなので、**Skillのdescriptionを適切に書くことの方が重要**です。 ([Visual Studio Code][2])

---

## 2. 「変更要求ファイルを必ず起点にする」は少し緩めてよいと思います

添付案では、

> 変更要求ファイルを必ず起点にする

という考えが強めですが、私はここを少し変更します。

今回のAgentは、次の2パターンに対応させるのが使いやすいです。

### パターンA：変更要求ファイルあり

```text
CR-0001_json-to-xml.md の変更内容を
関連ドキュメントへ反映してください。
```

これは大規模変更向けです。

### パターンB：直接指示

```text
ファイル出力形式をJSONからXMLへ変更しました。
関連する設計書、テスト仕様書、運用手順書を調査し、
必要箇所を更新してください。
```

こちらは小規模変更向けです。

したがって、Agentには、

```md
変更要求ファイルが指定された場合は、そのファイルを変更の基準とする。

変更要求ファイルがない場合は、ユーザーの指示から、
変更前・変更後・変更理由・影響範囲候補を整理して作業を開始する。
```

くらいがよいと思います。

**すべての変更でCRファイル作成を必須にすると、普段使いでは少し重くなる**可能性があります。

---

## 3. 一番重要なのは「単純な文字列置換をしない」というルールです

今回のAgentで最も危険なのは、

```text
JSON → XML
```

という指示を受けて、

```text
全ファイルから JSON を検索
↓
XML に置換
```

してしまうことです。

例えば調査報告書には、

> JSONを候補として調査したが、○○の理由により採用しなかった。

という記録を**残す必要がある**かもしれません。

そこで、Agentには次をかなり明確に書いた方がよいです。

```md
# 変更判断ルール

変更前の用語が含まれているという理由だけで、機械的な置換を行わない。

各記載について、以下のいずれかを判断する。

- 現在仕様として修正が必要
- 変更履歴・調査経緯として残す必要がある
- 比較対象や不採用案として残す必要がある
- 変更とは無関係である

意味を判断してから修正すること。
```

これは今回のAgentの品質をかなり左右すると思います。

---

## 4. 「影響調査」と「修正」を明確に分けた方がよいです

添付案では既にある程度分かれていますが、さらに明確に、

```text
① 変更内容整理
    ↓
② 関連ファイル検索
    ↓
③ 影響判定
    ↓
④ 修正計画
    ↓
⑤ ファイル修正
    ↓
⑥ 再検索
    ↓
⑦ 整合性確認
```

とするとよいです。

特に最後の**再検索**は重要です。

例えばJSON→XML変更なら、修正後に再度、

```text
JSON
.json
application/json
Serialize
Deserialize
```

などを検索します。

そこで残っている記述について、

> 修正漏れなのか
> 意図的に残している過去経緯なのか

を確認します。

# AgentとSkillの分担について

私は次のように整理するのが最も分かりやすいと思います。

## Agent側

```text
役割
変更内容を受け取る
↓
変更の意味を理解する
↓
影響範囲を探索する
↓
必要なドキュメントを判断する
↓
順番に更新する
↓
整合性を検証する
↓
結果を報告する
```

つまり、**プロジェクト全体の作業責任者**です。

## Skill側

```text
調査報告書では何を見るか
見積書では何を見るか
要件定義書では何を見るか
基本設計書では何を見るか
……
テスト仕様書では何を見るか
……
```

つまり、**変更波及作業の標準手順書・チェックリスト**です。

この分け方なら、将来的に別Agentから同じSkillを利用することもできます。Agent Skillsは、専門的なワークフローを再利用可能な形で定義し、必要時に読み込む用途として説明されています。 ([Visual Studio Code][2])

# カスタムエージェント名の候補

私なら次の3候補です。

## 第1候補：`doc-sync.agent.md`

一番おすすめです。

```text
doc-sync.agent.md
```

良い点は、短くて覚えやすいことです。

Agent選択画面でも、

```text
Ask
Plan
Edit_Light
Doc Sync
```

のように並べやすいと思います。

役割も「関連ドキュメントを同期させる」という意味で直感的です。

---

## 第2候補：`change-impact-updater.agent.md`

```text
change-impact-updater.agent.md
```

こちらは役割がかなり明確です。

> 変更
> → 影響範囲を調査
> → 関連ファイルを更新

という今回の処理内容を正確に表しています。

ただ、少し長いです。

---

## 第3候補：`doc-change-propagator.agent.md`

```text
doc-change-propagator.agent.md
```

添付案の名前です。これもかなり良いと思います。

`propagate` は「変更を波及させる」という意味なので、技術的には今回の目的に非常に合っています。

ただし日常的にAgentを選択するとき、

```text
Doc Change Propagator
```

は少し硬い印象があります。

# 私ならこの構成にします

```text
.github/
├── agents/
│   └── doc-sync.agent.md
│
└── skills/
    └── doc-change-propagation/
        └── SKILL.md
```

名前の役割を少し変えています。

### Agent

```text
Doc Sync
```

ユーザーが普段呼び出すものなので、短い名前。

### Skill

```text
doc-change-propagation
```

内部的な能力なので、処理内容を正確に表す名前。

この組み合わせが一番よいと思います。

## 全体評価

添付案は**考え方としてはかなり良い**です。

私なら、大きく作り直すのではなく、

1. Agentの `skills:` 指定を見直す
2. CRファイルを必須ではなく推奨にする
3. 機械的な文字列置換を禁止する
4. 「影響調査 → 修正 → 再検索」の流れを明確化する
5. Agentを軽め、詳細なチェック観点をSkill側へ寄せる

という調整をします。

**名前については `doc-sync.agent.md` を第一候補として推します。**

次の段階では、この方針で実際に使える `doc-sync.agent.md` の全文を作るのがよさそうです。
