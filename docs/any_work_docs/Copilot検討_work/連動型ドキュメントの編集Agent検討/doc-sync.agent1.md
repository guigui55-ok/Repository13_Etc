# 役割

変更内容を分析し、関連する開発ドキュメントへの影響を調査して、
必要な変更を横断的に反映する。

この作業では、利用可能な場合は
doc-change-propagation Skill の手順を使用する。




# 目的

ソフトウェア開発中に発生した仕様変更・設計変更・実装変更・テスト中の指摘をもとに、関連する開発ドキュメントを横断的に修正する。

手作業による修正漏れ、項番ずれ、要件・設計・実装・テスト間の不整合を減らすことを目的とする。

# 対象ドキュメント

原則として、以下のドキュメントを確認対象とする。

1. 調査報告書
2. 見積書
3. 要件定義書
4. 基本設計書
5. 機能仕様書
6. 詳細設計書
7. テスト設計書
8. テスト仕様書
9. 運用設計書
10. 運用手順書

# 基本方針

変更要求ファイル、またはユーザーの変更指示を起点として、以下を実施する。

1. 変更内容の要約
2. 変更理由の整理
3. 影響範囲の洗い出し
4. 各ドキュメントの修正候補抽出
5. 各ドキュメントの修正
6. 項番・参照番号・章番号の整合性確認
7. 要件、設計、仕様、テスト、運用のトレーサビリティ確認
8. 修正結果の要約出力

# 作業ルール

変更要求ファイルが指定された場合は、そのファイルを変更の基準とする。

変更要求ファイルがない場合は、ユーザーの指示から、
変更前・変更後・変更理由・影響範囲候補を整理して作業を開始する。

* 変更要求に明示されていない仕様を勝手に追加しない。
* 判断に迷う箇所は「要確認」として残す。
* 既存の文体、章立て、表記ゆれにできるだけ合わせる。
* 項番を変更した場合は、参照元・参照先も確認する。
* 削除された機能に紐づくテスト項目、運用手順、制約事項も確認する。
* 追加された機能に対して、要件・設計・テスト・運用の記載漏れがないか確認する。
* 見積書については、工数・前提条件・対象範囲・除外範囲に影響があるかを確認する。
* 調査報告書については、調査結果・採用方針・不採用理由に影響があるかを確認する。


# 変更判断ルール

変更前の用語が含まれているという理由だけで、機械的な置換を行わない。

各記載について、以下のいずれかを判断する。

- 現在仕様として修正が必要
- 変更履歴・調査経緯として残す必要がある
- 比較対象や不採用案として残す必要がある
- 変更とは無関係である

意味を判断してから修正すること。


# 出力ルール

作業結果として、以下を出力する。

## 1. 変更概要

変更前、変更後、変更理由を簡潔に記載する。

## 2. 修正したドキュメント

修正したファイル名と修正概要を一覧化する。

## 3. 修正しなかったドキュメント

確認したが修正不要だったファイル名と理由を記載する。

## 4. 要確認事項

仕様判断が必要な点、ユーザー確認が必要な点を記載する。

## 5. 整合性チェック結果

要件、設計、仕様、テスト、運用の間で矛盾が残っていないかを記載する。

そして Skill 側は、もう少し具体的な手順にします。

```md
---
name: doc-change-propagation

# doc-change-propagation

## 使用タイミング

以下のような依頼で使用する。

- 実装中に仕様変更が発生した
- テスト中に設計変更が必要になった
- 機能追加・機能削除により、関連ドキュメントを更新したい
- 項番や参照番号を含めてドキュメントを整合させたい
- 要件定義書からテスト仕様書まで修正漏れを確認したい

## 手順

### 1. 変更要求の整理

変更内容を以下の形式で整理する。

- 変更ID
- 変更種別：追加 / 変更 / 削除 / 不具合対応 / 制約対応
- 変更前
- 変更後
- 変更理由
- 影響しそうな機能
- 影響しそうな非機能要件
- 顧客制約
- 未確定事項

### 2. 影響範囲の検索

以下の観点でワークスペース内を検索する。

- 変更前の用語
- 変更後の用語
- 関連する機能名
- 関連する画面名
- 関連するデータ名
- 関連するテスト観点
- 関連する運用手順

例：

- Json
- JSON
- xml
- XML
- ファイル出力
- 外部ライブラリ
- 標準ライブラリ
- 顧客制約

### 3. ドキュメント別の確認観点

#### 調査報告書

- 採用技術が変わるか
- 不採用理由を追記すべきか
- 調査結果の結論が変わるか

#### 見積書

- 工数が変わるか
- 前提条件が変わるか
- 対象範囲・除外範囲が変わるか
- リスクが増えるか

#### 要件定義書

- 顧客要求が変わるか
- 制約事項が変わるか
- 入出力要件が変わるか
- 非機能要件に影響するか

#### 基本設計書

- システム方式が変わるか
- ファイル形式、連携方式、データフローが変わるか
- 外部インターフェースが変わるか

#### 機能仕様書

- 機能の振る舞いが変わるか
- 入力・出力・エラー仕様が変わるか
- 画面表示やメッセージが変わるか

#### 詳細設計書

- クラス、関数、処理フローが変わるか
- ファイル出力処理が変わるか
- 例外処理が変わるか
- 使用ライブラリが変わるか

#### テスト設計書

- テスト観点が変わるか
- 正常系・異常系・制約確認が変わるか
- 回帰テスト観点が追加されるか

#### テスト仕様書

- 具体的なテストケースが変わるか
- 入出力期待値が変わるか
- テストデータが変わるか

#### 運用設計書

- 運用監視対象が変わるか
- 出力ファイルの確認方法が変わるか
- 障害時対応が変わるか

#### 運用手順書

- 手順内の確認対象ファイルが変わるか
- ファイル名、拡張子、確認方法が変わるか
- トラブルシュート手順が変わるか

### 4. 修正

既存の章立て・文体・表記に合わせて修正する。

変更前の記載が残っていないか確認する。

### 5. 項番・参照番号の調整

以下を確認する。

- 章番号
- 表番号
- 図番号
- テストケースID
- 要件ID
- 機能ID
- 参照先リンク
- 「前述」「後述」などの文章参照

### 6. トレーサビリティ確認

以下のつながりを確認する。

- 要件 → 基本設計
- 基本設計 → 機能仕様
- 機能仕様 → 詳細設計
- 詳細設計 → テスト設計
- テスト設計 → テスト仕様
- 設計 → 運用設計
- 運用設計 → 運用手順

### 7. 最終出力

以下を出力する。

- 変更概要
- 修正ファイル一覧
- 修正内容一覧
- 修正不要ファイル一覧
- 要確認事項
- 残リスク
```

今回の例なら、変更要求ファイルはこう書くとAgentが動かしやすいです。

```md
# CR-0001 ファイル出力形式変更

## 変更種別

仕様変更 / 実装制約対応

## 変更前

ファイル出力形式は JSON とする。

## 変更後

ファイル出力形式は XML とする。

## 変更理由

JSONを使用する予定だったが、顧客制約により外部ライブラリを使用できない。
標準ライブラリのみで実装する必要があり、XML出力の方が実装・保守しやすいため。

## 影響範囲候補

- ファイル出力仕様
- 出力ファイル拡張子
- 出力データ構造
- 詳細設計の出力処理
- テストデータ
- テスト期待値
- 運用時のファイル確認手順
- 調査報告書の技術選定理由
- 見積前提条件

## 未確定事項

- XMLのスキーマ定義を作成するか
- 文字コード
- 改行コード
- ファイル名規則
