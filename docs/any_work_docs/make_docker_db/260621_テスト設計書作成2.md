はい、その認識で概ね合っています。ただし、**「要求仕様書（要件定義書）の各機能と1対1対応」だけでは少し不足**します。

実務では、**要件 → 設計 → テスト** のトレーサビリティを意識して作成します。

関係を図にすると、

```text
要件定義書
    │
    ├── 要件ごとにテストが存在するか？
    │
基本設計書
    │
    ├── 設計した機能・画面・IF・DB・遷移がテストされるか？
    │
詳細設計書
    │
    ├── 実装ロジックや異常処理まで必要なら確認
    │
テスト設計書
    │
テスト仕様書
```

## 要件定義書との対応

ここが一番重要です。

例えば

| 要件ID  | 要件             |
| ----- | -------------- |
| RQ-01 | CSVを出力できる      |
| RQ-02 | UTF-8で保存する     |
| RQ-03 | 存在しないフォルダならエラー |

これらは**必ず何らかのテストケースで確認**します。

つまり

```
RQ-01
  ├─正常系
  ├─大量データ
  └─空データ

RQ-02
  ├─文字コード確認

RQ-03
  ├─異常系
```

というように紐付きます。

---

## 基本設計書との対応

こちらも非常に重要です。

基本設計書には

* 画面
* ボタン
* 項目
* 遷移
* ファイル仕様
* IF仕様
* DB仕様

などがあります。

例えば

```
画面A

[CSV出力]

クリックすると保存ダイアログ表示
```

なら

```
・ボタン押下
・保存ダイアログ表示
・キャンセル
・保存成功
・保存失敗
```

などのテストになります。

つまり

**設計したものは全部テスト対象**

という考えです。

## 詳細設計書との対応

これは会社によります。

詳細設計書まで見るケースでは

```
if (aaa == null)
```

なら

```
nullになるケース
```

```
switch

case1
case2
case3
```

なら

```
case1
case2
case3
default
```

なども確認します。

単体テストではここまで見ることが多いですね。

## テスト設計書を作る時の考え方

私はいつも次の順番で考えます。

```
① 要件を見る
    ↓
何を保証したい？

② 基本設計を見る
    ↓
どんな機能がある？

③ 詳細設計を見る
    ↓
どんな条件分岐がある？

④ リスクを考える
    ↓
壊れやすい所は？

⑤ テスト観点を作る
```

## テスト仕様書を作る時

テスト設計書で作った観点を、

```
観点
↓

具体的操作

↓

期待結果

↓

テストデータ
```

まで落とし込みます。

例えば

設計書では

```
CSV出力する
```

だけですが、

仕様書では

| No | 操作      | 期待結果      |
| -- | ------- | --------- |
| 1  | CSV出力押下 | 保存ダイアログ表示 |
| 2  | 保存実行    | CSV作成     |
| 3  | 上書き     | 確認ダイアログ   |
| 4  | キャンセル   | 作成されない    |
| 5  | 保存先なし   | エラー表示     |

というレベルになります。

## 実務では「トレーサビリティマトリクス」を作ることもある

大規模案件では、次のような対応表を作成することがあります。

| 要件ID  | 基本設計  | 詳細設計  | テスト設計 | テスト仕様      |
| ----- | ----- | ----- | ----- | ---------- |
| RQ-01 | BD-12 | DD-34 | TD-08 | TS-001～008 |
| RQ-02 | BD-15 | DD-40 | TD-10 | TS-009～012 |

これがあると、

* **要件に対してテスト漏れがないか**
* **設計変更時にどのテストを修正すべきか**
* **今回のように仕様変更が発生したとき、どのドキュメントに影響するか**

を追跡しやすくなります。

実は、このトレーサビリティの考え方は、先ほどご相談いただいた「変更内容を各種ドキュメントへ自動反映するCopilot Agent」と非常に相性が良いです。要件ID・設計ID・テストIDなどの関連付けをAgentがたどれるようにしておけば、変更時に影響箇所を漏れなく洗い出しやすくなります。
