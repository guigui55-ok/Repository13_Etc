
### 1. 高可用性構成（High Availability / HA）

**意味：障害が起きても止まりにくい構成**です。

サーバーやDBが壊れても、別系統へ切り替えてサービス継続できるようにします。

例（DBの場合）：

* DBサーバーA（本番）
* DBサーバーB（待機）

Aが故障
↓
自動切替
↓
Bで継続

こういう構成です。

代表例：

* Active-Standby（主系＋待機系）
* Active-Active（両方稼働）
* DBレプリケーション
* クラスタ構成
* フェイルオーバー

今回の学習用VMなら、見積外に入れているのは妥当です。
高可用性までやると、

* VM追加
* ネットワーク設計
* DB同期
* 障害試験

まで増えるので、工数がかなり膨らみます。

### 2. PoC実施（Proof of Concept）

**意味：本格実装前に「実現可能か」を小さく検証すること**です。

日本語だと、

* 概念実証
* 技術検証
* 試作検証

と言われます。

今回の見積書だと：

> Docker理解不足 → 再構築発生 → PoC実施

なので、

本構築前に例えば：

□ Ubuntu VMを1台作る
↓
□ Dockerだけ入れる
↓
□ nginxコンテナ起動
↓
□ 再起動後も動く確認

ここまでやって、
「いけそう」
を確認してから本構築へ進む、という意味です。

実務だと、

* 新DB採用可否
* クラウド移行可否
* 新FW導入可否

でよくやります。

---

### 3. Go / NoGo（ゴー・ノーゴー）

**意味：次工程へ進むか、止めるかの判断基準**です。

実務では「Go判定」「Go/NoGo会議」などと言います。

今回の記載：

> Ubuntu起動
> Docker起動
> DB接続成功
> …

これを全部満たす
→ **Go（進行・完了）**

満たさない
→ **NoGo（中止・継続作業）**

イメージ：

```
要件定義
 ↓ Go
設計
 ↓ Go
構築
 ↓ Go
テスト
 ↓ Go
完了
```

実務では判定会（レビュー）で、

* 品質OK？
* 工数超過してない？
* リスク許容？
* 次工程進める？

を確認します。

---

今回の見積書だと、この3つの使い方は概ね自然です。
ただ、1点だけ改善するとしたら、

現在：

> Docker理解不足 → 再構築発生 → PoC実施

より、

改善案：

> Docker理解不足 → 再構築発生 → **小規模PoC実施（Hello World構築→破棄）**

の方が、「何をやるか」が明確になって実務ドキュメントっぽくなります。
