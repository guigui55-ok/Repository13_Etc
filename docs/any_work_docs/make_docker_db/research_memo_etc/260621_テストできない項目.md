これ、実務だとかなり重要な論点です。
結論からいうと、

> **「テストできない＝要件にしてはいけない」ではないです。**
> ただし、**どう確認するか（検証方法）を別途決める必要があります。**

前に話した「測れる要件が良い」は原則ですが、現実には測りにくい要件もあります。

考え方としてはこう整理します。

```text id="67rtjw"
要求
↓
確認可能？
↓
YES → テスト条件へ
NO
↓
代替確認方法ある？
↓
YES → レビュー・分析・監視等
NO
↓
リスク受容・注記
```

確認方法はテストだけではありません。

| 確認方法     | 例       |
| -------- | ------- |
| 実機テスト    | 接続、性能   |
| レビュー     | 設計妥当性   |
| 解析・計算    | 容量、負荷   |
| 運用監視     | 長期安定性   |
| 実績・標準準拠  | 既知構成利用  |
| 受容（リスク化） | 災害、未知障害 |

---

例1：今回の案件（復旧）

要求：

```text id="3j6yfa"
障害時に環境復旧できること
```

でも停電やディスク故障を再現したくない。

→ テスト困難。

対応：

```text id="26cnho"
復旧手順レビュー
＋
再構築手順確認
＋
スナップショット復元確認
```

で代替。

---

例2：性能

要求：

```text id="vft1uj"
快適に利用できること
```

測れない。

改善：

```text id="czkq9o"
Docker起動後1分以内
SQL接続30秒以内
```

へ変更。

---

例3：可用性（典型）

要求：

```text id="k4i0xu"
1年間安定稼働
```

学習案件では検証不可。

対応：

```text id="l7mwbm"
既知の安定版を使用
レビュー確認
運用観測
```

---

ここで実務でよく使う分類があります。

| 検証可能性   | 扱い      |
| ------- | ------- |
| 直接テスト可能 | テスト仕様へ  |
| 間接確認可能  | レビュー・解析 |
| 長期観測のみ  | 運用へ移管   |
| 現実的に不可  | 制約・リスク  |

今回のVM案件に落とすと、例えば、

```text id="hx8sui"
要件:
長期運用できること

確認方法:
長期試験は対象外
既知安定版利用
構築手順整備

記録先:
制約・前提条件
```

みたいにします。

なので答えとしては、

**機能として必要なら残す。ただし「テストできない」では終わらず、レビュー・解析・運用・リスク受容のどれで保証するかを決める**、です。

これ、要件定義→テスト設計の境界を考える時のかなり実務的なポイントです。
