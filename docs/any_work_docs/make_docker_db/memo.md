# 非機能要件の検討方法
まず最初に、機能要件から一旦離れる

何のために使う？
↓
利用シーンは？
↓
困ることは？
↓
それを防ぐ条件は？
↓
非機能要件

## 手順1 使われ方（利用シナリオ）を書く

利用者:
自分

利用:
VM起動
↓
Ubuntu操作
↓
Docker起動
↓
SQL Server接続
↓
開発
↓
停止

## 手順2 困ることを列挙する

VM起動が遅い
↓
性能

Dockerで固まる
↓
性能・容量

構築手順忘れる
↓
保守性

壊れて復元不可
↓
可用性

将来別OSへ移れない
↓
拡張性

操作方法忘れる
↓
運用性


## 手順3 分類する（品質特性）
典型例
| 観点     | 問い        |
| ------ | --------- |
| 性能     | 遅くないか     |
| 可用性    | 止まって困らないか |
| 保守性    | 直せるか      |
| 運用性    | 管理できるか    |
| 拡張性    | 増やせるか     |
| セキュリティ | 守れるか      |
| 移植性    | 環境変更できるか  |
| バックアップ | 戻せるか      |

## 手順4 測定可能にする

VM起動後5分以内に作業可能

Docker起動後1分以内に利用可能

再構築手順で1時間以内に復旧可能

※考え方１
性能
   一般的なと書くのはNG　×
   必要な時間を想定する　→
   自分の環境などで計測　→　問題なさそうなら、この計測した時間を基準に明記

※考え方２
復旧
　→学習用がメイン用途のため、復旧手順および復旧にかかる時間は考慮しない（環境構築手順によって再構築を想定）
↓
可用性・復旧要件は最小とする。
障害発生時はバックアップ復旧ではなく、
構築手順による再構築を基本とする。


※考え方３
例えば
VMが止まったら困ることを考える
↓
どのような状況、どのようなことをしたら止まるか？を考える
↓
ホストPCのリソース不足（または、リソースの使い過ぎ）
災害時など
↓
これにどう対応できるか？
↓
対応できること AND 機能に書いていないこと → 非機能要件
対応できないこと → 要件定義に明記

| 事象       | 原因     | 対応     | 分類   |
| -------- | ------ | ------ | ---- |
| VM重い     | メモリ不足  | VM停止運用 | 性能要件 |
| VM破損     | 設定変更   | 再構築    | 運用要件 |
| 停電       | 外部要因   | 受容     | 制約   |
| Docker停止 | 設定ミス   | 手順化    | 保守性  |
| 容量不足     | ディスク枯渇 | 容量監視   | 運用性  |

   → テスト困難。
