この考え方、かなり良いです。
実務でも「要件定義を書く人の頭の中」を明文化すると、まさにそこに近いです。

結論からいうと、機能要求の作り方は、

> **目的 → 利用シーン → 要求 → 機能 → 分割判断 → 記載**

という流れにすると、粒度が安定します。

ポイントは、**最初から機能一覧を書かない**ことです。

## 私なら要件定義の作成ルールをこう決めます

### ルール1 まず要求を書く（機能を書かない）

最初に「何をしたいか」を文章で書く。

例（今回）：

```text id="r83ehm"
サーバー構築を実務風に学習したい
Dockerを利用したい
DB接続を確認したい
再構築可能にしたい
```

まだ機能にしません。

---

### ルール2 利用シナリオを書く

誰が、何を、どの順で使うか。

例：

```text id="tfgvfx"
利用者:
自分

利用手順:
VM起動
↓
Ubuntuログイン
↓
Docker起動
↓
SQL Server接続
↓
学習
↓
停止
```

---

### ルール3 シナリオから機能候補を抽出

動詞を抜き出します。

```text id="d1i6vh"
起動
ログイン
導入
接続
確認
停止
```

↓

機能候補

```text id="kgj1gq"
VM構築
OS導入
Docker利用
DB利用
接続確認
```

---

### ルール4 分割ルールを適用する

ここが粒度ルールです。

私は実務で次を基準にします。

**1機能 = 次のどれかが変わったら分割**

| 分割条件     | 例              |
| -------- | -------------- |
| 責務が変わる   | 構築／接続          |
| 利用者が変わる  | 管理者／利用者        |
| 失敗原因が変わる | OS失敗／DB失敗      |
| 受入条件が変わる | 起動確認／接続確認      |
| 別テストになる  | Docker確認／SQL確認 |

逆に同じならまとめます。

## ルール5 各機能は1行で説明できるか確認

最後に確認します。

悪い例：

```text id="u6c88y"
環境をいい感じに構築する
```

良い例：

```text id="bwd4uv"
SQL Serverを導入し接続可能とする
```

私はこのルールを文章化するとこうします。

機能要求作成ルール

1. コンセプト・ヒアリング内容から要求を抽出する
2. 利用シナリオを作成する
3. シナリオ中の操作・目的を機能候補として抽出する
4. 以下のいずれかが異なる場合は機能を分割する

   * 責務
   * 利用者
   * 障害原因
   * 受入条件
   * テスト方法
5. 各機能は1文で説明可能な粒度とする
6. 各機能は受入条件を設定可能であること
7. 実装手順や設定値は記載せず設計工程へ委譲する

このルールを先に決めると、今後の要件定義・基本設計・テスト仕様の粒度が揃いやすくなります。
