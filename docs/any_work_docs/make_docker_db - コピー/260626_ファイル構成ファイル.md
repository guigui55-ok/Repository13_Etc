これは **Agent や Skill が参照するコンテキスト** なので、Instructions や Agent 本体とは分離しておくのは良い設計だと思います。

私なら、**「プロジェクトの構造・役割を説明するファイル」** として、以下のような名前をおすすめします。

### 第1候補（おすすめ）

`project-structure.md`

内容が一目で分かります。

```text
.github/
├── context/
│   ├── project-structure.md
│   ├── architecture.md
│   ├── coding-rules.md
│   └── glossary.md
```

---

### 第2候補

`workspace-map.md`

VSCode/Copilotらしい名前です。

中身は

* フォルダ構成
* 各プロジェクトの役割
* 依存関係

などを書きます。

---

### 第3候補

`repository-map.md`

GitHub寄りの表現です。

リポジトリ全体を説明するイメージになります。

---

### 第4候補

`project-overview.md`

構成だけではなく

* プロジェクト概要
* フォルダ構成
* 起動方法

なども書きたい場合はこちら。

---

## 配置場所

私は **`.github/context/`** をおすすめします。

```text
.github/
├── agents/
├── skills/
├── prompts/
├── instructions/
└── context/
    ├── project-structure.md
    ├── architecture.md
    ├── project-rules.md
    └── terminology.md
```

これは **Copilotの予約フォルダではなく、自分で管理するためのフォルダ**です。

Agentからは

```md
まず以下を参照してください。

- context/project-structure.md
- context/architecture.md
```

のように書けば十分です。

---

## 私ならさらに分割する

最初は `project-structure.md` 1つでも十分ですが、規模が大きくなるなら役割ごとに分けます。

```text
context/
├── project-structure.md   ← フォルダ構成・各プロジェクト説明
├── architecture.md        ← システム構成
├── naming.md              ← 命名規則
├── terminology.md         ← 用語集
├── workflow.md            ← 開発フロー
└── dependencies.md        ← プロジェクト依存関係
```

こうすると、Agentは必要なファイルだけ読むよう指示できるため、不要なコンテキストを減らしやすくなります。

## あなたのケースなら

これまでのお話では、

* サーバー
* 既存Editionクライアント
* 別Editionクライアント
* インストーラー
* ツール
* テスト
* ドキュメント

といった複数プロジェクトが同一ワークスペースに存在するとのことでした。

そのため、最初の1ファイルは

> **`project-structure.md`**

にして、

* フォルダ名
* 役割
* 実行ファイル
* 依存関係
* 「どの案件で触ることが多いか」

まで書いておくと、Agent・Skill・Promptのすべてから再利用しやすい「共通コンテキスト」として活用しやすくなると思います。
