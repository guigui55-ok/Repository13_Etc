まず質問1から。

> 前提条件って、ちょっとした概要っていう意味ですかね？

→ **近いですが、少し違います。**

前提条件は、

> **この設計が成立するために、先に決まっている・変えない条件**

です。

概要は「何を作るか」、前提条件は「どんな条件の上で作るか」です。

例えば今回。

概要：

```text id="m97yyj"
Hyper-V上にUbuntu＋Docker＋SQL Server環境を構築する
```

前提条件：

```text id="xj2cy3"
ホストOSはWindows11
Hyper-V利用
SQL Server採用済み
学習用途
本番運用対象外
```

違いを図にすると、

```text id="nifpk0"
目的
↓
要件定義（何を作る）
↓
基本設計
├ 概要（どういうもの）
├ 前提条件（変えない条件）
├ 方針（どう考える）
└ 設計（どう構成する）
```

なので、前回の基本設計の「前提条件」は少し多めでした。
厳密には、

* 前提条件
* 設計方針

を分けてもよいです。

「機能要件ごと」だけではなく、

**要件全体を設計観点へ変換する**

私はこう考えています。

```text id="sl8y4o"
要件定義
↓
何を作るか
↓
基本設計
↓
どう構成するか
↓
詳細設計
↓
どう設定するか
```

機能要求を例にすると。

要件：

```text id="uw5dy7"
Dockerを利用できること
```

基本設計：

```text id="1vl5g9"
Dockerを導入する
Composeは対象外

```

詳細設計：

```text id="0v0pm0"
Docker Engine 28.x

サービス起動設定
```

つまり、

```text id="2z9u90"
要件
↓
方式
↓
設定
```

です。

あと、設計で「理由」は結構重要です。

おすすめの順番はこれです。

```text id="6xt3xt"
① 要件
↓
② 設計判断
↓
③ 理由
↓
④ 制約
↓
⑤ 詳細
```

今回なら、

```text id="0p3ru3"
要件:
Docker利用可能

設計:
VM内導入

理由:
将来DB追加を考慮

制約:
単一VM

詳細:
詳細設計へ委譲
```

この流れで書くと、あとで読み返して「なぜそうしたか」が残ります。

```text id="8ntv77"
設計書の基本的な考え方

必要に応じて、
概要
前提条件
設計方針
採用理由
制約事項
を記載し、
詳細な設定値は詳細設計へ委譲する。
```
