とても良い質問です。
ここは「テスト設計書を書く方法」を知ると、要件定義・設計・テストが全部つながります。

結論からいうと、テスト設計は、

> **要件や設計から「壊れたら困ること」を抽出して、何をどう確認するかを決める作業**

です。

そして実際は、あなたの想像通り、

```text
アウトライン作成
↓
詳細化
```

で進めます。

ただ、アウトラインは「画面一覧」や「機能一覧」ではなく、**観点一覧**から作ります。

私ならこう進めます。

---

## Step1 テスト対象を決める（何を見るか）

最初に成果物を並べます。

今回なら。

```text
要件定義
↓
基本設計
↓
詳細設計
↓
構築手順
```

↓

テスト対象抽出

```text
VM
Ubuntu
Docker
SQL Server
SSMS
ドキュメント
```

まだテストケースは作りません。

---

## Step2 観点を決める（何を確認するか）

ここがアウトラインです。

私はまずこの順で見ます。

```text
存在
↓
利用
↓
連携
↓
異常
↓
運用
```

意味はこうです。

| 観点 | 見ること     |
| -- | -------- |
| 存在 | 作られているか  |
| 利用 | 使えるか     |
| 連携 | 他と動くか    |
| 異常 | 失敗時どうなるか |
| 運用 | 継続できるか   |

今回だと、

```text
VM
├ 作成されている
├ 起動できる
├ 再起動できる
└ 復旧できる

Docker
├ 導入済
├ 起動可能
├ 利用可能
└ 再起動可能
```

これがアウトラインです。

---

## Step3 観点を展開する（詳細化）

ここで初めてテスト設計になります。

例。

```text
SQL Server利用可能
↓
観点分解

存在
・インストール済

利用
・起動

連携
・SSMS接続

異常
・認証失敗

運用
・再起動
```

まだ手順は書きません。

---

## Step4 優先順位を付ける

全部やると膨れます。

私はこれで絞ります。

```text
失敗影響 × 発生頻度
```

例。

| 対象     | 頻度 | 影響 | 優先 |
| ------ | -: | -: | -: |
| VM起動   |  高 |  高 |  高 |
| Docker |  高 |  高 |  高 |
| ログ     |  低 |  低 |  低 |
| 監視     |  低 |  低 | 除外 |

---

## Step5 テスト方式を決める

最後です。

観点ごとに確認方法を決めます。

```text
VM起動
→ 目視

Docker
→ CLI

SQL
→ SSMS

再構築
→ 手順レビュー
```

ここまででテスト設計完成。

---

その後でテスト仕様へ落とします。

```text
観点:
SQL接続

↓

手順:
SSMS起動
接続

↓

期待:
接続成功
```

---

今回の案件に当てると、私はまずこういうアウトラインを作ります。

```text
テスト設計アウトライン

1 VM
  1-1 作成
  1-2 起動
  1-3 再起動

2 Ubuntu
  2-1 ログイン
  2-2 更新

3 Docker
  3-1 導入
  3-2 起動
  3-3 利用

4 SQL Server
  4-1 起動
  4-2 接続

5 SSMS
  5-1 接続
  5-2 操作

6 運用
  6-1 手順確認
  6-2 再構築確認
```

ここから詳細を詰める感じです。

一言でまとめると、

> **アウトラインは「対象 × 観点」で作り、詳細は「確認方法 × 期待結果」で詰める**

です。
