ここは「非機能要件とは何か」ではなく、**人間がどう考えて作るか**にフォーカスして説明します。

結論からいうと、非機能要件は、

> **「そのシステムが現実で困らずに動く条件」を洗い出して、数値やルールに落とす作業**

です。

機能要件が「何をするか」なら、非機能要件は「どうあるべきか」です。

---

## まず最初に、機能要件から一旦離れる

初心者がやりがちなのが、

```text
Dockerを入れる
SQL Serverを入れる
↓
じゃあ性能は…
```

という考え方です。

実務では逆で、

```text
何のために使う？
↓
利用シーンは？
↓
困ることは？
↓
それを防ぐ条件は？
↓
非機能要件
```

です。

---

## 手順1 使われ方（利用シナリオ）を書く

まず運用場面を想像します。

今回なら、

```text
利用者:
自分

利用:
VM起動
↓
Ubuntu操作
↓
Docker起動
↓
SQL Server接続
↓
開発
↓
停止
```

ここではまだ要件を書きません。

---

## 手順2 困ることを列挙する

次に、

「これ何が起きたら嫌か？」

を書きます。

例：

```text
VM起動が遅い
↓
性能

Dockerで固まる
↓
性能・容量

構築手順忘れる
↓
保守性

壊れて復元不可
↓
可用性

将来別OSへ移れない
↓
拡張性

操作方法忘れる
↓
運用性
```

ここが一番重要です。

---

## 手順3 分類する（品質特性）

困りごとをグループ化します。

典型例はこれです。

| 観点     | 問い        |
| ------ | --------- |
| 性能     | 遅くないか     |
| 可用性    | 止まって困らないか |
| 保守性    | 直せるか      |
| 運用性    | 管理できるか    |
| 拡張性    | 増やせるか     |
| セキュリティ | 守れるか      |
| 移植性    | 環境変更できるか  |
| バックアップ | 戻せるか      |

---

## 手順4 測定可能にする

ここが要件化です。

悪い例：

```text
快適に動作する
```

良い例：

```text
VM起動後5分以内に作業可能

Docker起動後1分以内に利用可能

再構築手順で1時間以内に復旧可能
```

実務で最後にやるチェックがあります。

```text
この要件を満たしたか、
テストできるか？
```

テストできない要件は、非機能要件として弱いです。

たとえば、

❌「使いやすい」
→ 測れない

⭕「30分以内に初回構築可能」
→ 測れる

今回の案件なら、**「困ること→品質分類→測れる条件」** の順で考えるとかなり実務寄りになります。

## ※考え方1（性能）

ここは少しだけ直したいです。

今の案：

```text
一般的な時間を計測
↓
時間を明記
```

実務寄りにすると、

```text
利用目的を決める
↓
困る時間を決める
↓
実測して妥当性確認
```

です。

なぜかというと、「一般的」は案件で変わるからです。

例えば今回。

悪い例：

```text
起動時間 60秒以内（一般的だから）
```

良い例：

```text
学習開始まで待ち時間を減らしたい
↓
VM起動後5分以内に作業開始可能
```

つまり、

**要件 → 測定**

であって、

**測定 → 要件**

ではないことが多いです。

あなたの案：

```text
学習用途
↓
復旧手順・時間は考慮しない
↓
再構築想定
```

今の書き方だと、

```text
復旧を考えていない
```

実務っぽくすると、

```text

```

になります。

つまり、

「不要」ではなく、
**「再構築を復旧方法として採用」**

です。

## ※考え方2（かなり良い）

これ、実務では結構近いです。

少し修正するとこうです。

```text
困る事象
↓
原因候補
↓
対策候補
↓
対策する？
↓
YES → 要件化
NO → 制約・前提・リスクへ
```

ここがポイントです。

今の案：

```text
対応できない
↓
要件定義へ記載
```

少し違います。

対応できないものは、要件ではなく、

* 制約
* 前提条件
* リスク
* 対象外

へ逃がします。

例。

```text
VM停止
↓
停電
↓
UPS導入不可
↓
受容

→ 制約:
停電対策対象外
```

別例。

```text
VM停止
↓
メモリ不足
↓
対処可能

→ 非機能要件:
同時起動VM数を制限
```

---

今回の案件に当てるとこうなります。

| 事象       | 原因     | 対応     | 分類   |
| -------- | ------ | ------ | ---- |
| VM重い     | メモリ不足  | VM停止運用 | 性能要件 |
| VM破損     | 設定変更   | 再構築    | 運用要件 |
| 停電       | 外部要因   | 受容     | 制約   |
| Docker停止 | 設定ミス   | 手順化    | 保守性  |
| 容量不足     | ディスク枯渇 | 容量監視   | 運用性  |

なので、今の考え方はかなり筋が良いです。

特に今回の一番大事な気づきは、

> **非機能要件は「全部解決する表」ではなく、「どこまで責任を持つか決める表」**

ということです。
